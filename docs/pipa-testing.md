# Pipa testing strategy

This is the reusable testing procedure for runtime changes, including one Pipa release with v1/v2 HTTP adapters. The implementation plan's Verification Contract owns the detailed feature matrix and release gates. New harness files and commands below are planned deliverables, not capabilities already implemented.

## Three kinds of proof

1. **Deterministic:** `npm test` verifies implementation behavior, failure paths, concurrency, scheduling with controlled clocks, and process ownership. `npm run test:pack` verifies the installed npm package. Run the existing Linux/macOS/Windows CI matrix.
2. **Real OpenCode:** Qualify the exact CLI/client versions with isolated profile/database paths. Prove prompt admission versus final output, history migration, permissions/forms, attachments, cancellation, background work, and model switching against the real server.
3. **Real Slack:** Prove message routing, scheduled delivery, result-thread continuation, artifacts, and detached restart in the selected channel. An HTTP fixture cannot substitute for these round-trips.

Run the deterministic baseline before implementation. Record existing failures and compare after the change. Never describe unexecuted real-service checks as passed.

## Shared contract and pinned engine harness

Both adapters must pass the same semantic scenarios: exact prompts, session continuation, completion/error handling, question/permission lifecycle, cancellation, supersession, file handling, and cleanup. Native HTTP requests/responses/events use independent v1/v2 fixtures; expected data must not be generated by the adapter being tested. Version selection is exercised through the production facade.

Build the fixture contract and real-engine runner before the port. Record the current v1 baseline and current v2 failures rather than emulating a missing adapter. The harness-delivery step can finish with those named baseline incompatibilities; release qualification cannot. Rerun the identical production-path cases as the adapters and live evaluator land.

Planned harness ownership:

| Surface | Responsibility |
|---|---|
| `test/helpers/runtime-fixture.mjs` | Private roots, controlled environment, process/port tracking, bounded polling, cross-platform teardown |
| `test/helpers/opencode-contract.mjs` | Shared product assertions independent of native endpoint spelling |
| `test/opencode-contract.test.mjs` | Both fixture generations in default `npm test` |
| `scripts/test-opencode-matrix.mjs` | Pinned real engines and installed Pipa tarball, with a deterministic local model |
| `scripts/verification/opencode-release-cases.mjs` | Shared production-path real-engine scenarios, outside default test discovery |
| `scripts/slack-release-eval.mjs` | Serial real Slack/provider cases, routine evaluator reuse, independent restart observation, evidence |

Keep the default `npm test`/`npm run test:pack` lane free of downloaded engines and live credentials. The planned `test:engines` lane qualifies pins **1.18.35, 1.19.0, and 2.0.29** against Socket-owned, Managed, and attached modes on Linux/macOS/Windows where supported. Node 22 is the baseline. The downloaded executable's identity and package integrity must match the selected cell; no global executable is replaced.

The Socket-owned engine cell composes the real Pipa application, executor, scheduler and state with injected fake Chat/auth. Managed cells use the actual installed CLI and detached restart chain. Attached cells use an independently launched server and prove ownership preservation. Real Socket CLI restart and visible Slack controls still require the live lane; fake Chat does not prove them.

Mock only the model for deterministic real-engine cases. Drive real tool/question/permission flows and use stage barriers to force retries, lost responses, disconnections, revocation, and cancellation races. Tests must not impose their deadlines on valid production turns. Use controlled clocks for DST/long horizons and actual scheduler dispatch for short one-time/recurring runs.

The former spike's 58 comparison checks and 55 routine/restart/CLI baseline passes are supporting evidence, not a substitute for running this harness on the implemented dual-adapter package.

## Isolate local state and recover migration failures

Each case gets private HOME/USERPROFILE, XDG config/data/cache/state, temporary directory, PIPA_HOME, workspace, artifacts, and supported engine database/config overrides. Isolate Windows app-data roots where used and retain required SystemRoot/ComSpec/PATHEXT plumbing. Construct child environments from an allowlist rather than inheriting the operator's credentials, attach URL, proxies, or Node options. Assert the product's intended non-Slack integration-variable inheritance separately with synthetic sentinels.

Generate synthetic old-version data with each pinned v1 engine. Stop/checkpoint it, preserve a pristine copy and needed database companions, then migrate only a disposable copy to v2. Continue the same session IDs/history and verify Pipa's thread mappings, routines, configured permissions, and documented remembered-approval reset. Restart v2 again. Rollback restores the matched old snapshot; it never opens v2-written data with v1.

Force process death around context registration, prompt admission, pending approval, and completion. Pipa must clean up only its owned instruction/admission recovery state before accepting new work. Do not silently replay side effects or claim exactly-once delivery across crashes. The scheduler's existing crash-window semantics remain documented.

## Choose a live-test environment

Use a separate Slack test app and channel when available. Reusing an existing app is also supported: stop its existing Pipa process before another process uses the same Socket Mode credentials. The operator supplies app identities and the test destination through private configuration; this guide has no workspace-specific defaults.

- Verify the original process is stopped; a lock in a different `PIPA_HOME` does not prove that there is no other consumer of the same Slack app.
- Run the candidate from a separate private Pipa profile and disposable working directory. Restrict its channel allowlist to the test channel.
- Isolate OpenCode database and configuration too. `PIPA_HOME` isolates Pipa state, not OpenCode state. Use the qualified OpenCode release's supported path overrides.
- Supply app credentials through private profile configuration. Keep tokens out of command arguments, evidence, repository files, and agent child environments.
- Use a private snapshot for migration/rollback checks. Never run destructive migration experiments against the only copy of existing conversations or routines.
- When the run ends, stop its owned processes, record cleanup, and return control to the operator. Never leave two consumers of the app running.

## Evaluator inputs

Copy the committed `.env.example` to the gitignored `.env.test` and fill in the environment values for your workspace. Alternatively, inject the same environment variables from your shell or CI secret store. Do not add a second credentials-file format or a dotenv dependency.

Run the existing routine evaluator with Node 22's native environment-file support:

```sh
node --env-file=.env.test scripts/slack-routine-eval.mjs
```

This command requires the candidate Socket profile to be configured and running first. `PIPA_HOME` selects that private profile; its saved config contains the Slack app/bot credentials. OpenCode's database/config isolation uses the qualified release's supported path overrides separately. `.env.example` contains names and blank values only; never commit populated env files or credentials. The broader v2 evaluator will use the same input convention.

Existing `scripts/slack-routine-eval.mjs` uses:

| Input | Purpose |
|---|---|
| `SLACK_TEST_CHANNEL_ID` | Exact destination selected by the operator |
| `SLACK_PIPA_BOT_USER_ID` | Identifies candidate Pipa replies |
| `SLACK_USER_TOKEN` | Existing human-message evaluation path |
| `PIPA_HOME` | Selects the candidate's private profile |

The routine evaluator currently assumes a running Socket profile and tests preview, explicit confirmation, scheduled nonce delivery, duplicate detection, and test-routine cleanup. It does not currently cover the full migration feature matrix.

The compatibility plan adds the pinned matrix and a broader Slack evaluator. Reuse the existing routine flow rather than duplicating scheduler logic. Planned bot-sender support can use a token from another existing app; it must use that app's actual message `bot_id`, allowed only in the candidate profile. Pipa ignores its own messages, so it cannot act as its own test sender.

A sender bot cannot stand in for an authorized human clicking a button or submitting a modal. Use human-assisted real interaction checks where necessary and deterministic handler tests for repeatable authorization/error coverage. Mark which checks are automated and which require a responder.

Run live tests sequentially by engine generation if they reuse an app. Use an app-scoped workflow concurrency lock without cancelling an active run. Paginate Slack history/replies, honor `Retry-After`, and match the exact sender/channel/thread/nonce. Validate the preview creates nothing and that the saved prompt, schedule, timezone, destination and lifecycle match the confirmed input. Keep paid/provider-backed and Slack jobs protected and manually/release-triggered; fork PRs get no secrets.

## Automatable scenarios

- A mention produces one reply; a follow-up reuses the session. Two independent threads do not block each other.
- A newer same-thread message supersedes long work without stale replies or success reactions.
- A preview leaves routine state unchanged. A confirmed one-time routine runs from the scheduler without a manual `run` request and delivers exactly one nonce result.
- Recurring runs preserve exact prompt/destination. Replies continue the result session. Deactivation/deletion and destination revocation prevent stale delivery.
- A long routine never overlaps itself; different routines can overlap. Controlled-clock tests cover DST, end dates, missed occurrences, and pending run-request recovery.
- Incoming attachment limits are checked against metadata and downloaded bytes. Both adapters accept 20 MiB and reject one byte above it; outgoing artifact limits remain separate. Measure decoded file bytes and also qualify data-URI/JSON overhead and multiple native files.
- Generated artifacts match expected bytes/checksums. Failed upload yields one text fallback. Unsafe paths are rejected.
- A restart requested from Slack is observed by a process outside the runtime being restarted. Verify durable outcome, old-process exit, replacement PID/generation, readiness, one ready notice, and a working follow-up.
- The replacement survives the observer/worker ending. Failed/unready replacements never report success and clean up their owned children/locks. Attached servers remain running.
- Reconnection/reload does not duplicate admitted work or delivery; pending controls are reconciled.

Use the migration plan's full feature matrix for provider/MCP/plugin/definition checks and native delegated-work compatibility. Preserve Pipa's current Slack delivery contract; testing native background execution does not introduce new acknowledgements, follow-up notifications, or background-job controls. A short nonce match alone does not establish all-feature coverage.

## Evidence and cleanup

For each scenario, record `PASS`, `FAIL`, or `BLOCKED`, versions/platform, expected and observed results, and a sanitized evidence reference. Record Slack thread/message references, session identity where relevant, duplicate counts, restart request/generation identity, and cleanup outcome.

Evidence also names the adapter selected, connection mode, package version, automated versus human-assisted coverage, and documented native `NOT_APPLICABLE` cases. Common behavior cannot be marked not applicable. Live model switching is v2-specific; ordinary v1 questions, permissions and routines are not optional.

Use a unique run nonce. Clean up only that run's test routines, files, and owned processes. Leave unrelated channel history and saved routines alone. Keep raw evidence private; share a sanitized summary. A failed cleanup makes the run fail. Missing credentials, a human responder, integration access, or platform evidence makes that coverage blocked.

Track and close all provider/stream listeners, process trees, ports, locks, staging/artifact paths and nonce-owned routines, including failure paths. Assert an attached engine survives Pipa stop before harness-owned teardown. Keep the test root only for explicitly retained sanitized diagnostics. A local loopback server/data-URI fixture is not proof of a remote filesystem or host; separately hosted deployment coverage remains an explicit gate.

Paid/model-backed and Slack checks are opt-in commands, not unconditional CI jobs. They are still required release-qualification evidence for affected features. The implementation handoff lists every passed, failed, and blocked feature rather than claiming success from a green unit suite alone.
